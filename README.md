A cleanroom, local re-implementation of the [Shaype B2B Operations API](https://developer.shaype.com/openapi/b2b-operations-api.json) for end-to-end testing of code that integrates with Shaype, on a developer machine. Stateful (customers, accounts, cards, transactions, holds, PayIDs, mandates, …), backed by SQLite (in-memory or file), with Cognito-style client-credentials auth and outbound webhook notifications. Not affiliated with Shaype. Not for production use.

Point your application at it instead of Shaype's staging environment: same paths, request and response shapes, status codes, `ErrorResponse` envelope and webhook payloads as the vendored specs in `spec/`, plus an `/_admin` API that lets tests reset state, move time and inspect the webhooks that were sent.

## Running the server

From a checkout:

```sh
npm install
npm run dev -- --port 8080 --webhook-url http://localhost:3000   # tsx, no build step
npm run dev -- --help                                             # every flag with its environment variable
```

As a built CLI (`npm run build` produces `dist/`; the package's `bin` is `shaype-local`):

```sh
npm run build && npm pack                     # -> shaype-local-api-0.1.0.tgz
cd ../your-app && npm install -D ../shaype-local-api/shaype-local-api-0.1.0.tgz
npx shaype-local --port 8080 --webhook-url http://localhost:3000
```

Every flag has an environment variable; a flag wins over its variable.

| Flag | Environment variable | Default | Meaning |
|---|---|---|---|
| `-p, --port <n>` | `SHAYPE_LOCAL_PORT` | `8080` | Listen port. |
| `--host <host>` | `SHAYPE_LOCAL_HOST` | `127.0.0.1` | Bind address. |
| `--db <path\|:memory:>` | `SHAYPE_LOCAL_DB` | `:memory:` | SQLite database; a file path keeps state across restarts. |
| `-w, --webhook-url <url>` | `SHAYPE_LOCAL_WEBHOOK_URL` | none | Base URL of your application; see [Webhooks](#webhooks). |
| `--client-id <id>` | `SHAYPE_LOCAL_CLIENT_ID` | `local-client` | The one accepted OAuth client id. |
| `--client-secret <s>` | `SHAYPE_LOCAL_CLIENT_SECRET` | `local-secret` | Its secret. |
| `--no-auth` | `SHAYPE_LOCAL_AUTH=false` | auth on | Accept `/v0` and `/v1` calls without a bearer token. |
| `--log-level <level>` | `SHAYPE_LOCAL_LOG_LEVEL` | `info` | pino level (`silent`, `error`, `warn`, `info`, `debug`). |
| `--webhook-max-attempts <n>` | `SHAYPE_LOCAL_WEBHOOK_MAX_ATTEMPTS` | `5` | Delivery attempts per notification before it is marked `failed`. |
| `--webhook-backoff-ms <ms>` | `SHAYPE_LOCAL_WEBHOOK_BACKOFF_MS` | `200` | First retry delay; doubles on every further attempt. |
| `--webhook-timeout-ms <ms>` | `SHAYPE_LOCAL_WEBHOOK_TIMEOUT_MS` | `10000` | Per-delivery request timeout; a timeout is retried like a network error. |
| `--async-delay-ms <ms>` | `SHAYPE_LOCAL_ASYNC_DELAY_MS` | `0` | Delay of the platform's asynchronous effects; see [Asynchronous effects and the clock](#asynchronous-effects-and-the-virtual-clock). |
| `--default-risk-level HIGH\|LOW` | `SHAYPE_LOCAL_DEFAULT_RISK_LEVEL` | `HIGH` | Risk level of new accounts. `HIGH` (Shaype's default) sets every limit to 0. |
| `--emit-customer-inactive` | `SHAYPE_LOCAL_EMIT_CUSTOMER_INACTIVE=true` | off | Also send `CUSTOMER_STATUS_UPDATED {INACTIVE}` when closing the last account deactivates a customer. |

`GET /_admin/health` answers once the server is ready.

## Authentication

With auth on (the default), every `/v0/*` and `/v1/*` call needs a bearer token from the Cognito-style client-credentials endpoint. Send the client as form fields or as HTTP Basic:

```sh
curl -s -X POST http://127.0.0.1:8080/oauth2/token \
  -H 'content-type: application/x-www-form-urlencoded' \
  -d 'grant_type=client_credentials&client_id=local-client&client_secret=local-secret'
# {"access_token":"eyJhbGciOiJIUzI1NiIs…","expires_in":3600,"token_type":"Bearer"}

TOKEN=$(curl -s -X POST http://127.0.0.1:8080/oauth2/token -u local-client:local-secret -d grant_type=client_credentials | jq -r .access_token)
curl -s http://127.0.0.1:8080/v1/products -H "authorization: Bearer $TOKEN"
```

- A missing, invalid or expired token is a `403` `ErrorResponse` (`FORBIDDEN: Missing bearer token`, `… Invalid token`, `… Token expired`); the spec declares 403 on every operation and never 401.
- Bad credentials answer `400 {"error":"invalid_client"}`, a grant other than `client_credentials` `400 {"error":"unsupported_grant_type"}`.
- Tokens live 3600 s **on the virtual clock**: moving the clock forward by an hour or more expires them, so fetch a new one after a large clock move.
- Tokens are signed with a per-process key: they do not survive a restart, but they do survive `/_admin/reset`.
- `/oauth2/token` and `/_admin/*` never need a token.

## Webhooks

Start the server with `--webhook-url <base>` (your application's base URL, the one you register with Shaype). Every notification is POSTed as JSON to

```
<base>/api/hay/v0/communications/notification
```

with a body shaped like `NotificationDto` in `spec/notification-webhooks.json`. (`<base>/api/hay/v1/communications/notification` is used for the v1 types `BATCH_COMPLETED` and `PERK_ORDER_UPDATE`, which belong to out-of-scope features and are never emitted.)

- Envelopes are compact: absent properties are omitted, not sent as `null`.
- `idempotencyKey` identifies the notification and stays the same across retries: deduplicate on it.
- `actionOwner` is `CLIENT` when one of your API calls caused the change and `PLATFORM` for the platform's own behaviour (onboarding outcome, first posting activating an account, closure cascade, direct-entry progress, …).
- Notifications are delivered asynchronously, one at a time, in creation order; a notification waiting for a retry does not hold back later ones.
- A `401`, `403`, `429`, `5xx` answer, a network error or no answer within `--webhook-timeout-ms` is retried after `--webhook-backoff-ms`, then twice that, and so on, up to `--webhook-max-attempts` attempts in total. Any other non-2xx answer is final (`failed`).
- Retry delays are real time, not virtual time: freezing or moving the clock does not hold a retry back (`nextAttemptAt` shows the virtual-clock equivalent).
- With a file `--db`, notifications still queued when the server stopped are sent again when it restarts with `--webhook-url`; without it they are kept as `stored`.
- Every notification is stored whether or not it was delivered; without `--webhook-url` they are only stored (`status: "stored"`). Inspect them with `GET /_admin/notifications`.

A throw-away receiver that prints what it gets:

```sh
node -e "require('node:http').createServer((req, res) => { let b = ''; req.on('data', (c) => (b += c)); req.on('end', () => { console.log(req.method, req.url, b); res.end() }) }).listen(3999)"
```

## The admin API

`/_admin/*` is for tests and never needs a token.

| Endpoint | Does |
|---|---|
| `GET /_admin/health` | `{ status: "ok", version, now, clockFrozen, db, auth, webhookUrl, operations, stubbed }`. |
| `GET /_admin/operations` | `{ handled: [...], stubbed: [...] }`: which operationIds a domain implements and which answer from the stub. |
| `POST /_admin/reset` | Deletes every row (customers, accounts, cards, transactions, notifications, …), cancels pending asynchronous work and webhook deliveries (the one in flight is aborted: nothing enqueued before the reset is sent after it) and resets the clock. Sequences restart (the first account number is `10000001` again). |
| `POST /_admin/flush` | Runs due work, then waits (up to 10 s) until no asynchronous work due within about 9 s is pending and no notification is queued; answers `{ "status": "idle" }`. Steps further out (e.g. a Utilities mock with `settlementDelayInSeconds: 120`) stay pending and are counted in its `deferred` field; run them with `POST /_admin/clock {"advanceMs": …}`. Call it after an action and before asserting. |
| `GET /_admin/clock` | `{ now, frozen }`. |
| `POST /_admin/clock` | Body `{ "advanceMs": n }`, `{ "set": "<ISO date-time>" }` (jump, keep ticking), `{ "freeze": "<ISO date-time>" }` (pin) or `{ "reset": true }` (back to real time). Runs whatever became due. |
| `GET /_admin/notifications` | Stored notifications, oldest first (`order=desc`: newest first): `{ id, version, type, payload, status, attempts, lastStatus, lastError, createdAt, nextAttemptAt, deliveredAt, seq }`. Filters: `type`, `status` (`queued`, `delivered`, `failed`, `stored`), `sinceSeq`, `limit` (default 1000). |
| `GET /_admin/notifications/:id` | One notification (`id` = its `idempotencyKey`). |
| `DELETE /_admin/notifications` | Forgets every stored notification: `{ deleted: n }`. |
| `POST /_admin/notifications/:id/redeliver` | Queues it for delivery again. |
| `POST /_admin/notifications/flush` | Waits for webhook delivery only. |
| `POST /_admin/scheduled-payments` | Creates a scheduled payment (Shaype creates these only through its portal). Body: `{ accountId, customerHayId?, amount, currency?, description?, reference?, type?: RECURRING\|ONE_TIME, frequency?: WEEKLY\|FORTNIGHTLY\|MONTHLY\|QUARTERLY, startDate, endDate?, numberOfPayments?, shouldCancelOnFailure?, recipient: { recipientType: ACCOUNT\|BPAY, recipientName?, recipientAccountNumber?: { branchNumber, accountNumber }, bpayDetails?: { billerCode, billerReference } }, replaces?: <hayId> }`. `201` with the `HayScheduledPayment`, and a `SCHEDULED_PAYMENT` notification; `replaces` updates an `ACTIVE` schedule in place (`200`). Due payments run on the clock. |

## Test-steering conventions

| To get | Do |
|---|---|
| An onboarded customer | Create it with any email: onboarding runs asynchronously and ends `ACTIVE` with `ONBOARDING_PASSED` then `CUSTOMER_STATUS_UPDATED {ACTIVE}` (`PLATFORM`). |
| A referred customer | Put `+referred` in the email's local part (`jane+referred@example.com`): `REFERRED`, `ONBOARDING_FAILED {state: KYC_AML_SCAN}`. Clear it with the KYC approval endpoints (`POST /v1/kyc/{customerId}/onboarding/{amlKycCheck,documentCheck,sanctionCheck}/approval`). |
| A rejected customer | `+rejected` in the email: `REJECTED`, `ONBOARDING_FAILED {state: DOCUMENT_SCAN}`. |
| A customer you drive yourself | `+pending` in the email: it stays `PENDING_APPROVAL` with no onboarding webhook; set the status with `PATCH /v0/customers/{id}/status`. |
| Money movement on a new account | New accounts have risk level `HIGH`, which makes every limit 0 and refuses every movement (a credit answers `REFUSED_MAX_BALANCE_EXCEEDED`). Set `LOW` with `PATCH /v0/accounts/{id}/riskLevel` `{ "level": "LOW", "reason": "…" }`, or start the server with `--default-risk-level LOW`. |
| An account with money | `POST /v1/transactions/credit` (a `GENERAL_CREDIT`; the first posting turns an `APPROVED` account `ACTIVE`). |
| A BSB that fails | `999999`: `verifyBranchIdentifier` answers `{ "enabled": false }`, `checkBsbIsSupportedByPayTo` `{ "supported": false }`, and a direct debit whose recipient BSB is `999999` is `REJECTED` at once. |
| A biller that fails | Biller code `000000` is deactivated: `validateBpay` answers 422, `makeBpayPayment` `REFUSED_BPAY_INVALID_BILLER_CODE`. Any other 4–10 digit code is a valid biller; the five Shaype staging billers (`7773`, `93849`, `93880`, `600015`, and the deactivated `1016`) keep their documented rules. |
| A declined card transaction | The card mock endpoints (`/v0/utils/generate-auth-hold`, `generate-card-transaction`, `generate-update-auth-hold`) take `declineReason`: `CARD_EXPIRED`, `WRONG_CVV`, `CVV_BLOCKED`, `INCORRECT_PIN`, `ALLOWED_PIN_RETRIES_EXCEEDED`, `INVALID_MERCHANT`, `CARD_IS_NOT_ACTIVE` or `RESTRICTED_CARD` force a processor decline: nothing is held and the `TRANSACTION` webhook carries the refused outcome. The card's own state declines too: a `BLOCKED` card, an expired one, a card awaiting activation, or a channel switched off in its payment preferences (card-not-present, contactless, magnetic stripe and ATM are off by default). |
| A daily-limit refusal | Limits are rolling 24 h windows on the virtual clock. Transfers out are capped at 100,000 a day (not listed by `getAccountLimits`), and so are inbound credits (`TOP_UP_PER_DAY`: general credits, NPP / DE credits, PayTo and internal transfers in; `BANK_TRANSFER_TOP_UP_PER_DAY`: NPP / DE / PayTo credits), so fund a large fixture over more than one day; account-level limits can be lowered with `PUT /v1/accounts/{id}/limits/{limitType}` and `PATCH /v0/accounts/{id}/max-balance`. |
| A PayTo payment outcome | Put `paymentstatus:<status>[&<status>]` or `paymentstatus:timeout_rjct` in the payment's (or the mandate's) description, as on Shaype staging. |

## Asynchronous effects and the virtual clock

Effects Shaype performs asynchronously happen asynchronously here too: the onboarding outcome, the account-closure cascade (account `CLOSED`, cards `INACTIVE`, customer `INACTIVE`; from the `202` on, the account refuses money movements with `REFUSED_ACCOUNT_CLOSED`), direct-debit progress (`ACCEPTED` → `SUBMITTED` → `COMPLETE`, one step at a time), FX child-account provisioning, PayTo payment progress and the card settlement of the mock purchase. By default (`--async-delay-ms 0`) they run right after the response; `POST /_admin/flush` waits for them and for the resulting webhooks. With a file `--db`, effects still pending when the server stops run after it restarts (the virtual clock itself starts again at real time).

Every such effect is also due on the **virtual clock**. Start the server with a large delay (e.g. `--async-delay-ms 3600000`) and nothing happens until your test moves the clock, so every intermediate state can be observed:

```sh
curl -s -X POST localhost:8080/_admin/clock -H 'content-type: application/json' -d '{ "advanceMs": 3600000 }'
```

In that mode do not call `/_admin/flush` while an effect is pending (it waits in real time and gives up with a 500 after 10 s); wait for the webhook instead. Time-driven jobs run whenever the clock moves and on every API request: card expiry and its reminders, scheduled payments, PayID timers, PayTo action expiry, due payments and validity ends. Remember that tokens expire on the same clock.

## Stub-only sections

Perks, FX, Liquidity, Click to Pay and Tokens are outside the local model (Merchant Category Codes serve a seeded ISO 18245 reference list): their operations validate the request like any other and answer with deterministic example data built from the response schema, with the header `x-shaype-local-stub: <operationId>`. `GET /_admin/operations` lists every stubbed operationId; an operation that a domain has not implemented yet is listed there too.

## Conventions

- **Amounts** are JSON numbers in the account currency with at most two decimals (`25.5`, not `"25.50"`); a request amount with more decimals is a `400`, never rounded. Request amounts on create operations are positive; the operation fixes the direction. Balances (`heldBalance`, `stacksBalance`, …) are reported positive. In webhooks `currencyAmount.amount` is signed: negative for debits, holds and settlements, positive for credits, refunds and hold releases. The Utilities card mocks take negative amounts, as the spec requires. PayTo amounts are decimal strings, as its DTOs declare.
- **Balances**: `totalBalance` = settled ledger (stacked money included) + overdraft limit; `availableBalance` = total − held − locked − stacks. A hold moves `held` and `available`; its settlement moves `total` and `held`.
- **Date-times** (`*DateTimeUtc`, `transactionTimeUtc`) are UTC with microseconds: `2026-09-24T10:37:24.981000Z`. Dates are `YYYY-MM-DD`. All of them come from the virtual clock.
- **Ids** are UUIDs (v4; PayTo mandate ids use the v1 layout and are also accepted in the 32-hex form). Every local account has BSB `636220` and an 8-digit account number from a sequence (`10000001`, `10000002`, …). Card tokens are 9 digits (`100000001`, …); only the PAN's last four digits are exposed; cards expire at the end of the month four years after issue.
- **Errors** use the `ErrorResponse` envelope `{ message, details, status, traceId }` with `status` as a string and `message` as `<REASON_CODE>: <text>`: `400` for malformed JSON, schema violations, bad uuids or enum values; `403` for auth; `404` `NOT_FOUND: <Entity> <id> not found` for unknown ids; `422` for business rules (`PERMISSION_DENIED`, `INVALID_STATE`, `ACCOUNT_CLOSED`, …); `409` only where the spec declares it (duplicate BPAY biller). Refused money movements are not errors: they answer `200` with an `outcome` such as `REFUSED_INSUFFICIENT_FUNDS`.
- **Idempotency**: create operations that take `idempotencyKey` replay the stored response for the same key and body, and answer `422 IDEMPOTENCY_KEY_REUSED` for the same key with a different body.
- **Lists** paged with `offset`/`limit` require both (`limit` 1–1000) and return bare arrays in creation order unless the operation sorts.

## Worked example

Customer → account → card → mock purchase → webhook, against `npm run dev -- --no-auth --port 8123 --webhook-url http://127.0.0.1:3999` with the receiver above listening on 3999 (with auth on, add `-H "authorization: Bearer $TOKEN"` to every `/v0` and `/v1` call).

```sh
BASE=http://127.0.0.1:8123
uuid() { node -e 'console.log(crypto.randomUUID())'; }

# 1. customer: PENDING_APPROVAL now, ACTIVE once the asynchronous onboarding ran
CUSTOMER=$(curl -s -X POST $BASE/v0/customers/create -H 'content-type: application/json' -d '{
  "idempotencyKey": "'$(uuid)'", "email": "jane@example.com", "customerTier": "STANDARD",
  "phoneNumber": { "countryCodePrefix": "+61", "numberAfterPrefix": "412345678" },
  "address": { "line1": "395 Bourke St", "townOrCity": "Melbourne", "administrativeRegion": "VIC", "postcode": "3000", "countryCodeIso": "AUS" },
  "customerDetails": { "firstName": "Jane", "lastName": "Citizen", "dateOfBirth": "1990-01-01" }
}' | jq -r .customerHayId)
curl -s -X POST $BASE/_admin/flush                  # {"status":"idle"}
curl -s $BASE/v0/customers/$CUSTOMER | jq -r .status  # ACTIVE

# 2. account (APPROVED, risk level HIGH), then risk level LOW so money can move
ACCOUNT=$(curl -s -X POST $BASE/v1/accounts -H 'content-type: application/json' -d '{
  "idempotencyKey": "'$(uuid)'", "accountHolderId": "'$CUSTOMER'", "accountHolderType": "CUSTOMER",
  "productId": "a1b2c3d4-0000-4000-8000-000000000001"
}' | jq -r .accountHayId)
curl -s -X PATCH $BASE/v0/accounts/$ACCOUNT/riskLevel -H 'content-type: application/json' \
  -d '{ "level": "LOW", "reason": "KYC complete" }'   # {"message":"Risk level changed successfully."}

# 3. top-up
curl -s -X POST $BASE/v1/transactions/credit -H 'content-type: application/json' -d '{
  "idempotencyKey": "'$(uuid)'", "accountHayId": "'$ACCOUNT'", "amount": 100,
  "counterpartName": "Payroll", "description": "Top-up", "transactionChannel": "MANUAL_ADJUSTMENT"
}'                                                   # {"outcome":"ACCEPTED","transactionId":"…"}

# 4. virtual card (ACTIVE at once); online (card-not-present) payments are off by default
CARD=$(curl -s -X POST $BASE/v0/cards/create -H 'content-type: application/json' -d '{
  "idempotencyKey": "'$(uuid)'", "accountId": "'$ACCOUNT'", "customerHayId": "'$CUSTOMER'", "cardType": "VIRTUAL",
  "firstName": "Jane", "lastName": "Citizen", "email": "jane@example.com", "pin": "1234",
  "phoneNumber": { "countryCodePrefix": "61", "numberAfterPrefix": "412345678" },
  "deliveryAddress": { "line1": "395 Bourke St", "townOrCity": "Melbourne", "administrativeRegion": "VIC", "postcode": "3000", "countryCodeIso": "AUS" }
}')
CARD_ID=$(echo "$CARD" | jq -r .cardHayId); CARD_TOKEN=$(echo "$CARD" | jq -r .cardToken)
curl -s -X PATCH $BASE/v0/cards/$CARD_ID/payment-preferences -H 'content-type: application/json' \
  -d '{ "cardNotPresentEnabled": true }'

# 5. mock purchase (Utilities API): a hold of 25.50, then its settlement
curl -s -X POST $BASE/v0/utils/generate-card-transaction -H 'content-type: application/json' -d '{
  "amount": -25.50, "cardToken": "'$CARD_TOKEN'",
  "merchantDetails": { "merchantName": "IGA (Mt Cotton)", "merchantId": "000009493578577", "merchantCategoryCode": "5411" }
}'
curl -s -X POST $BASE/_admin/flush
curl -s $BASE/v0/accounts/$ACCOUNT | jq -c '{ status, totalBalance, heldBalance, availableBalance }'
# {"status":"ACTIVE","totalBalance":74.5,"heldBalance":0,"availableBalance":74.5}

# 6. the webhooks, as stored (the receiver printed the same payloads)
curl -s "$BASE/_admin/notifications" | jq -c '.[] | [.type, .status, .payload.transactionEvent.transactionType, .payload.transactionEvent.currencyAmount.amount]'
# ["ONBOARDING_PASSED","delivered",null,null]
# ["CUSTOMER_STATUS_UPDATED","delivered",null,null]
# ["ACCOUNT_STATUS_CHANGE","delivered",null,null]            APPROVED
# ["ACCOUNT_STATUS_CHANGE","delivered",null,null]            ACTIVE (first posting)
# ["TRANSACTION","delivered","GENERAL_CREDIT",100]
# ["CARD_STATUS_CHANGE","delivered",null,null]
# ["TRANSACTION","delivered","CARD_TRANSACTION",-25.5]       the hold: isPending true, heldBalance 25.5
# ["TRANSACTION","delivered","CARD_TRANSACTION_SETTLED",-25.5]  holdHayId = the hold's transactionHayId
```

`test/scenario.test.ts` runs this journey and eight more (transfers, BPAY, PayID, direct debits on the clock, stacks, group accounts, account closure, reset) against a listening server with auth on and a real webhook receiver; `docs/testing.md` shows how to do the same from your own repository.

## How it works

- `spec/` holds the vendored OpenAPI files; `npm run gen` turns them into a routing table plus request/response JSON Schemas, so every one of the 169 operations validates input and serialises output exactly as the spec declares.
- Each domain under `src/domains/` implements its operations against SQLite and emits domain events; the webhook dispatcher turns those into Shaype-shaped notifications and delivers them.
- Design spec: `docs/superpowers/specs/2026-09-24-shaype-local-api-design.md`. Verified per-domain API maps: `docs/map/`. Each domain's `index.ts` header lists its contract deviations and the decisions it takes beyond the spec.
